# CallGuard 최종 실험 앱 (test-app)

보이스피싱 **개입 2종**의 효과를 **발신자 관계**(지인 / 모르는 사람) 2종 시나리오에서 측정하는
**앱 단독** 실험 도구입니다. 서버도, 공격자 브라우저도, 다른 기기도 필요 없습니다.
**폰 한 대로 실험이 끝납니다.**

> 기존 `callguard-experiment`(시나리오 4종 + 서버 + WebRTC + 공격자 브라우저)를 참고해
> 2026-09 팀 논의 확정안에 맞춰 새로 만든 별도 프로젝트입니다. `applicationId`가 달라
> 기존 앱들과 한 기기에 나란히 설치됩니다.

---

## 1. 실험 구조 한눈에

```
[발신] → [상대방 대본] → [개입 지점 대사] → [개입] → [참가자 반응 관찰·설문]
```

상대방이 처음부터 끝까지 **일방적으로** 말하고, 마지막 대사가 끝나는 순간 앱이 개입합니다.
참가자 대사는 대본에 없습니다 — 참가자가 무엇을 말하는가가 종속변수이기 때문입니다.

**탐지 알고리즘은 쓰지 않습니다.** 개입은 대본에 고정된 지점에서 발동하거나 연구자가
직접 누릅니다. 앱의 음성 인식은 개입을 **트리거하는 데 쓰이지 않고**, 참가자가 무엇을
말했는지 **기록·측정**하는 데만 쓰입니다.

## 2. 개입 조건 2종 (+ 통제)

| 조건 | 스피커 차단 | 마이크 차단 | 진동 | 경고음 | 안내 화면·TTS | 계속/종료 선택 | 강제 종료 |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| **1. 안내 + 계속/종료 선택** | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | — |
| **2. 안내 + 강제 종료** | ✅ | ✅ | ✅ | ✅ | ✅ | — | ✅ |
| **3. 무개입 (통제)** | — | — | — | — | — | — | — |

- **스피커 차단 · 마이크 차단 · 진동 · 경고음**은 두 개입의 **공통 상수**입니다. 조건이 아니라
  상수로 둔 이유는, 1과 2의 차이를 **"참가자에게 선택권을 주는가"** 하나로 귀속시켜야
  결과를 해석할 수 있기 때문입니다.
  (단위 테스트 `두 개입 조건의 공통 동작은 완전히 동일하다`가 이 불변식을 고정합니다)

### 개입은 처음부터 끝까지 **한 화면**입니다

```
개입 발동
  │
  ├─ 즉시: 스피커·마이크 차단 + 진동 + 경고음 + 안내 화면 표시
  │        (선택 버튼은 흐리게 — 아직 못 누름)
  │
  ├─ 0.9초 뒤: 화면에 적힌 그 문장을 TTS가 읽음
  │
  └─ 안내 끝:
       조건 1 → 같은 화면의 버튼이 활성화됨
       조건 2 → 통화가 끊김 (화면은 그대로)
```

안내 중과 안내 후에 **다른 화면을 띄우지 않습니다.** 화면이 바뀌면 참가자가 개입 내용이
아니라 화면 전환 자체에 반응하게 되어, 측정 대상이 흐려집니다. 조건 2에서 통화가 끊겨도
아래 화면만 조용히 바뀌고 참가자 눈에는 같은 화면이 유지됩니다.

버튼을 **숨겼다 나타내지 않고 흐리게 뒀다가 켜는** 이유도 같습니다 — 요소가 새로 생기면
그것이 또 하나의 화면 전환입니다. 다만 안내가 끝나기 전에는 누를 수 없게 해,
"안내를 듣고 판단한다"는 조건을 지킵니다.

### 안내 문구 (화면 = 음성, 시나리오와 무관하게 고정)

| 조건 | 문구 |
|---|---|
| **1** | "보이스피싱으로 의심되어 통화가 잠시 중단되었습니다. 상대방과 나의 음성이 서로 차단되어 전달되지 않습니다. 통화를 이어가시겠습니까?" |
| **2** | "보이스피싱으로 의심되어 통화가 종료되었습니다." |

화면에 뜬 글과 TTS가 읽는 말이 **같은 문장**입니다. 둘이 다르면 참가자가 어느 쪽을
근거로 판단했는지 알 수 없어집니다.

- **조건 1**에서 [통화 이어가기]를 고르면 **스피커·마이크 차단이 실제로 풀리고** 화면이 걷혀
  통화로 돌아갑니다. 차단이 남으면 이어가기를 고른 참가자가 듣지도 말하지도 못해
  선택지가 허울이 되고, 조건 1이 사실상 조건 2와 같아집니다.
- **조건 2는 안내가 끝난 뒤에** 통화를 끊습니다. 바로 끊으면 참가자가 사유를 듣지 못해
  "이유 없이 끊긴 통화"가 됩니다.
- **조건 3(무개입)** 은 개입 지점 도달 시각만 기록하고 화면도 띄우지 않습니다.

## 3. 시나리오 2종

| ID | 발신자 관계 | 상황 | 요구 | 대사 수 |
|---|---|---|---|---|
| `S1` | **지인** | 계좌가 잠겼다며 타인 명의 계좌로 급전 요구 | 50만 원 송금 | 5줄 |
| `S2` | **모르는 사람** | 은행 보안팀 사칭, 이상 거래 확인 | 계좌 비밀번호 앞 두 자리 | 4줄 |

**둘 다 진짜 사기입니다.** 달라지는 것은 *상대가 아는 사람으로 보이는가* 하나뿐이며,
저장된 이름이 뜨는 것만으로 경계가 늦어지는지를 봅니다.

> ⚠️ **이 구성으로 잴 수 없는 것**: 두 시나리오 모두 진짜 사기라 **개입은 항상 옳은 판단**입니다.
> "멀쩡한 통화를 얼마나 방해했는가"(과잉 개입 비용)는 측정되지 않습니다. 그 지표가 필요해지면
> 애매한 상황 대본을 `AttackerScriptCatalog`에 추가하면 됩니다 — 엔진은 손댈 필요가 없습니다.

### 발신자 표시

- **지인(S1)**: 연락처에 저장된 것처럼 **이름**이 크게 뜹니다. 기본값 `김민수`이며,
  **설정 화면 ③-1에서 참가자에 맞춰 바꿀 수 있습니다.**
- **모르는 사람(S2)**: 번호만 뜹니다.

### 기관명·번호는 전부 가상입니다

실존 금융기관 이름이나 실제 대표번호를 쓰면 이 저장소의 대본이 그대로 쓸 수 있는
피싱 템플릿이 되고 해당 기업을 사칭하는 자료가 됩니다. 팀 대본의 `__은행` 빈칸은
TTS가 읽어야 하므로 **충대은행**(가상)으로 채웠습니다. 참가자에게는 "모르는 번호에서
온 금융기관 전화"로만 보이면 충분하므로 실험 타당성에는 영향이 없습니다.

### 배정

시나리오 2종 × 개입 2종 = **4가지 조합**입니다. 순서는 참가자마다 다르게 배정하세요.

## 4. 상대방 음성 재생 방식 3종

설정 화면 ④에서 고릅니다. **세 방식 모두 같은 대본·같은 개입 지점**을 지나갑니다.

| 방식 | 동작 | 언제 쓰나 |
|---|---|---|
| **자동 재생 (TTS)** | 앱이 대본을 합성 음성으로 순서대로 읽음 | 기본값. 참가자 간 자극이 글자·타이밍까지 동일 |
| **녹음본 재생** | `assets/attacker/<시나리오ID>/` 의 실제 연기 녹음을 재생 | 실감나는 자극이 필요할 때 |
| **라이브 발화** | 앱은 소리를 내지 않음. 연구자가 옆에서 직접 말함 | 유연성이 필요하거나 녹음 준비가 안 됐을 때 |

### ⚠ 라이브 모드의 측정 한계

라이브 모드에서는 연구자가 대사를 읽고 **[다음 대사]를 누르는 순간** 개입이 발동합니다.
사람이 버튼을 누르는 지연(수백 ms~수 초)이 반응시간에 통째로 섞입니다.

앱은 이것을 로그에 명시합니다:
- `intervention_point_reached` 이벤트에 `liveManualAdvance: true`
- 요약의 `triggerLatencyControlled: false`
- 요약의 `lineShownToInterventionMs` = 대사가 뜬 시각 → 개입 발동까지 (= 연구자 지연)

**자동 재생 세션과 라이브 세션의 반응시간을 직접 비교하지 마세요.**
한 참가자 안에서는 모드를 섞지 않는 것을 권합니다.

### 녹음본 넣는 법

```
app/src/main/assets/attacker/S1/1.m4a
app/src/main/assets/attacker/S1/2.m4a   ... (대사 순서대로)
```

- 지원 확장자: `m4a`, `mp3`, `wav`, `ogg`
- **대사 한 줄 = 파일 한 개.** 통짜 파일 하나는 지원하지 않습니다 — 줄 경계가 없으면
  개입 지점을 앱이 알 수 없어 발동 시점이 참가자마다 흔들립니다.
- 파일이 없는 줄은 TTS로 대체되고 로그에 `attacker_line_fallback_tts`로 남습니다.
- **S1(지인)은 편한 반말, S2(모르는 사람)는 사무적인 존댓말로** 녹음하세요. 두 시나리오의 차이가 어조에서 나옵니다.
- 자세한 안내는 [`assets/attacker/README.txt`](app/src/main/assets/attacker/README.txt) 참고.

## 5. 처음 1회 설정

### 5-1. Android SDK 경로
Android Studio로 `test-app` 폴더를 한 번 열면 `local.properties`가 자동 생성됩니다.

### 5-2. Vosk 한국어 음성모델 (선택 — 없어도 앱은 동작합니다)

참가자 발화를 자동 인식해 숫자 유출을 잡으려면 모델이 필요합니다. 약 250MB라 저장소에 넣지 않았습니다.

1. https://alphacephei.com/vosk/models 에서 `vosk-model-small-ko-0.22.zip` 다운로드
2. 압축을 풀어 나온 폴더의 **내용물**을 `test-app/app/src/main/assets/model-ko/` 에 넣습니다.
   → 이 폴더 안에 `am/`, `graph/`, `ivector/`, `conf/` 가 바로 보여야 정상입니다.

> **모델이 없어도 실험은 진행됩니다.** 그 경우 앱은 **통화 녹음 + 연구자 수동 기록**으로 동작하고,
> 설정 화면 ⑤에 안내가 노란색으로 표시됩니다. 현장에서 모델 로드가 실패해도 세션을 버리지 않기 위한 설계입니다.

### 5-3. 폰 준비
- **한국어 TTS 음성 설치**: 설정 → 접근성 → TTS 출력 → 한국어 (라이브 모드 외 모든 모드에서 필요)
- 마이크·알림 권한 허용
- **실기기 권장** (에뮬레이터는 마이크·진동이 제대로 동작하지 않습니다)

## 7. 실험 진행 순서 (통화 1회 = 세션 1건)

```
① 설정 화면에서 참가자 ID · 순번 · 개입 조건 · 시나리오 · (지인이면) 이름 · 재생 방식 선택
        ↓
② [통화 시작] → 폰을 참가자에게 건넴 (참가자에게는 일반 통화 화면만 보임)
        ↓
③ 상대방 대사가 진행되고, 마지막 대사가 끝나면 개입 자동 발동
   (필요하면 우상단 ⚙ 버튼 → 연구자 패널 → [지금 개입 실행] 으로 수동 발동)
        ↓
④ 참가자 반응 관찰 → 연구자 패널 ⑥에서 원클릭 기록
        ↓
⑤ [세션 저장하고 종료] → 다음 세션 (순번이 자동으로 +1 됩니다)
```

### 연구자 패널

통화 화면 **우측 상단의 작은 ⚙ 버튼**을 누르면 열립니다. 다시 누르거나 [닫기]로 닫습니다.

| 섹션 | 기능 |
|---|---|
| ① 현재 상태 | 조건·시나리오·관계·요구 정보·재생 모드·개입/차단 상태·유출 감지·최근 발화 |
| ② 조건 선택 | 개입 방법·시나리오를 패널에서 직접 변경 (발동 전에만) |
| ③ 대본 진행 | 상황·핵심 요소 + 전체 대본 + 현재 위치. 라이브 모드의 [다음 대사] 버튼 |
| ④ 개입 실행 | **지금 개입 실행** (자동 발동과 완전히 동일, 세션당 1회) |
| ⑤ 후속 대사 | 참가자가 [통화 이어가기]를 골라 대화가 이어질 때 재생 |
| ⑥ 관찰 기록 | 경고 인지·말을 멈춤·계속 대답함 등 원클릭 기록 |
| ⑦ 유출 판정 | STT가 놓치거나 틀렸을 때 연구자가 직접 확정 (**주 지표**) |
| ⑧ 발화 수동 입력 | STT 미동작 시 참가자 발화를 대신 입력 |
| ⑨ 세션 종료 | 저장하고 종료 · 기록 화면 열기 |

## 8. 데이터

세션 하나 = **폴더 하나**입니다.

```
Android/data/com.example.callguard.testapp/files/sessions/
└── P07_T2_S1_POPUP_TTS_20260923_143012/
    ├── session.json     ← 조건 + 전체 이벤트 + 계산된 요약
    └── recording.wav    ← 통화 녹음 (16kHz mono, 녹음 켠 경우)
```

- **내보내기**: 설정 화면 → [저장된 세션 기록 보기 · 내보내기] → 세션별 또는 전체 내보내기.
  `adb pull`로도 회수할 수 있습니다.
- 기록 항목과 요약 지표 정의는 [`docs/log_schema.md`](docs/log_schema.md) 참고.

### 주 지표

| 지표 | 요약 필드 | 의미 |
|---|---|---|
| **유출 여부** | `leaked`, `leakAfterIntervention` | 요구 이후 실제로 정보를 불러줬는가 |
| **개입 반응시간** | `reactionTimeMs` | 개입 발동 → 참가자의 첫 반응. **발화 개시** 기준 |
| **판단 시간** | `decisionTimeMs` | 선택 버튼이 켜진 뒤 → 고를 때까지 (안내 재생 시간 제외) |
| **개입 수용/무시** | `choseContinue`, `callEndedBy` | 경고를 듣고도 통화를 계속했는가 |
| 개입 정확성 점검 | `pointToInterventionMs` | 개입 지점 → 발동 지연. 0에 가까워야 정상 |
| 모드 경고 | `triggerLatencyControlled` | false면 라이브 모드 — 반응시간 비교 금지 |

## 9. 프라이버시

- 앱에 **INTERNET 권한이 없습니다.** 참가자 음성이 기기 밖으로 나갈 수 없다는 것이 매니페스트 수준에서 보장됩니다.
- 녹음과 로그는 앱 전용 외부 저장소에만 남고, 연구자가 명시적으로 내보내기를 해야 다른 앱에 넘어갑니다.
- `.gitignore`가 세션 산출물과 `*.wav`를 커밋에서 제외합니다.

## 10. 알려진 한계 (분석 전에 읽어 주세요)

1. **스피커 차단은 실제 동작, 마이크 차단은 시뮬레이션입니다.** 상대방 음성은 이 폰이 재생하므로
   개입 순간 **실제로 소리가 멈춥니다**. 반면 통화 상대가 없으므로 마이크 차단은 화면 표시와
   로그상의 상태이고, 녹음과 인식은 차단 중에도 계속됩니다. 이것은 의도한 것입니다 —
   *차단 고지 후에도 참가자가 계속 말했는가*가 관측 대상이기 때문입니다.
2. **일방적 통보 구조입니다.** 실제 보이스피싱은 주고받는 대화지만, 이 실험은 "개입에 대한 반응"만
   측정하기 위해 대화를 단순화했습니다. 개입 이후 구간에서만 후속 대사로 제한적인 상호작용이 가능합니다.
3. **라이브 모드의 반응시간은 자동 모드와 비교할 수 없습니다** (§4 참고).
4. **과잉 개입 비용을 잴 수 없습니다.** 두 시나리오 모두 진짜 사기라 개입이 항상 옳은 판단이 됩니다
   (§3 참고).
